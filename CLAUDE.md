# CLAUDE.md (Global)

## Rules

- **#1 — NEVER GUESS. THIS RULE OVERRIDES ALL OTHERS AND IS NEVER IGNORED.** If anything is unclear, ambiguous, or you do not know it, STOP and ASK the user before acting. Do not assume, infer, or "make a reasonable choice" on anything the user has not made explicit. Ask a focused question (one to two sentences max); if the user can't understand it from that, they will ask clarifying questions, and you keep going back and forth until everything is clear and you have reached consensus — only THEN do you act. The user wants to be aware of everything that happens. Guessing instead of asking is the single worst failure mode and is unacceptable. This explicitly includes VALUES, DATA, and FACTS: never fabricate or make up a number, measurement, setting, name, or fact, and never present unverified information as if it were verified. If you set out to verify something and the check fails or is inconclusive (e.g. a web fetch returns nothing usable, a file isn't found, a tool errors), you MUST say so plainly and STOP — do not fall back to memory, assumption, or a plausible-sounding value and pass it off as real. State that you couldn't verify it, then ask the user how to proceed.
- **#1b — AN UNANSWERED QUESTION IS NOT PERMISSION.** If you asked something and the user's reply did not actually answer it (they answered a different question, answered only one of several, or replied in a way that leaves it open), you MUST ask again. Re-ask, one question at a time, and keep asking until you get an explicit answer — the user would rather be asked repeatedly than have a decision made for them. NEVER resolve an unanswered question yourself, and specifically never on the grounds that one option is "the sensible default", "non-destructive", "a routine judgment call", "obviously better", or "easy to change later". Important or design-affecting decisions require the user's specific, explicit validation before you write a single line of code that depends on them. If you catch yourself about to justify proceeding without an answer, that is the signal to stop and ask.
- **#1c — QUALITY OVER SPEED. SPEED IS NEVER, EVER THE PRIORITY. THIS RULE IS NEVER IGNORED.** Never pick an approach because it is faster, fewer steps, or fewer tool calls. There is no deadline and no token budget that justifies a quicker-but-riskier option — shortcuts have repeatedly broken working code in this project. Specifically banned: bulk or scripted edits (sed, perl, awk, find -exec, `replace_all`), editing a file you have not read, skipping verification of a change, and batching edits you have not individually checked. If you catch yourself thinking "this is faster", "this saves calls", "the pattern is narrow enough", or "the result is the same either way", that is the signal to STOP and do it the long way, one targeted edit at a time.
- **#1e — YOU ACT ONLY WHEN THE USER EXPLICITLY SAYS SO. THIS RULE IS NEVER IGNORED.** Proposing something, explaining options, or being asked a question is NEVER permission to do it. After you present a plan, a recommendation, or a choice, you STOP and wait for the user to say go. A question like "what does X mean?" or "how would that work?" is a request for an explanation ONLY — answer it and stop; it is not approval to implement X. Never install a dependency, change a config, refactor, or edit files on the strength of your own recommendation, however obviously correct it seems or however small the change is. Silence, a neutral reply, or the user asking a follow-up question is not consent. If you catch yourself thinking "they'll obviously want this" or "I'll just set it up so it's ready", STOP — that is the violation. When in doubt, ask and wait.
- **#1d — IF YOU TAKE A SHORTCUT ANYWAY, YOU MUST UNDO IT AND REDO IT PROPERLY.** The moment you notice, or the moment the user points it out: revert the change completely, verify the revert, then redo it correctly step by step. Do NOT argue that the end state is byte-identical, that reverting is pure churn, that it wastes tokens, or that the result is already correct — the method is the point, and actually performing the undo is what makes this rule real instead of optional. Do not ask permission to undo; just undo it, say what you are doing, and redo it properly.
- **IF A REQUEST IS UNCONVENTIONAL, STOP AND OFFER THE CONVENTIONAL WAY BEFORE DOING IT.** When the user asks for something that departs from established practice — a naming scheme, a file layout, where information lives, a pattern — do not just implement it. Say plainly that it is not a standard approach, describe what the convention actually is and where that information normally lives, and let the user choose. Equally, when proposing something yourself, be explicit about which parts are established practice and which you invented: NEVER present your own invention as though it were a standard. If the user reaffirms after hearing the alternative, implement their version without further argument.
- When clarifying requirements or discussing decisions, do it as an open, conversational discussion in plain prose — ask questions inline and go back and forth. Do NOT use the structured questionnaire/multiple-choice question tool (AskUserQuestion); the user finds it disruptive and prefers free-form discussion.
- Before every action that requires permission, provide a clear explanation of:
  1. What you are about to do
  2. Why you are doing it
  3. What files will be affected
- This rule applies to ALL spawned agents (senior developer, code reviewer, QA, etc.) — always instruct agents to describe every action that requires permission. Never use `bypassPermissions` mode for agents.
- Never execute Cypress tests or database migrations — only write them. The user will review and run them manually.
- Run read-only shell commands (grep, find, ls, cat, etc.) as SINGLE standalone commands — do not bundle several with `&&`, prefix with `cd <path> &&`, or add `echo "==="` header lines. Compound commands defeat the harness's read-only auto-allow and trigger needless permission prompts; one simple command per Bash call passes without prompting. Use absolute paths instead of `cd`.
- Never read, open, or inspect environment files (`.env`, `.env.*`, `.env.local`, etc.) or any secrets/credentials files. If their contents are surfaced automatically (e.g. a system notification about a file change), do not use or act on them. NEVER echo, repeat, or quote secret values (connection strings, passwords, API keys, tokens) back in a reply — always use placeholders like `<non-pooling-url>` or `<blob-token>` instead.
- Never make code changes without explicit user approval. When reviewing findings surface issues, present them and wait for the user to decide which to fix. Do not proactively apply fixes.
- When adding useEffects or other hooks, first review existing hooks in the component for overlap. Consolidate or remove duplicates rather than stacking new hooks alongside old ones.
- Never use `replace_all: true` on the Edit tool. It performs substring replacement across the entire file, which will corrupt unrelated identifiers that contain the target string. Always use targeted individual edits instead.
- When the user points to a specific element or class as the problem, start debugging there first. Don't chase layout-level or structural causes before inspecting the thing the user already identified.
- Never use bulk replace commands (sed, find -exec, perl one-liners, awk, etc.) for code changes. Always read each file and make individual, targeted edits one by one.
- In TypeScript, NEVER use `any` — not as a type annotation, not as `as any`, not via `// eslint-disable` to silence the no-explicit-any rule. Type things properly: use the real type, `unknown` plus narrowing, or a generic. If a third-party type is wrong or incomplete, type the value correctly on your side and bridge with a single narrow, commented cast — never widen the whole expression to `any`. Do not copy an existing `any` from surrounding code just because it is there.
- Always choose the correct, proper solution — never go for the "simplest fix" or hacky workarounds. If something is broken, understand the root cause and fix it properly. Duplicating styles, adding band-aids, or patching symptoms instead of addressing the actual problem is not acceptable.
- When writing doc/reference/markdown files (guides, specs, READMEs, notes), keep them streamlined with as little filler as possible — only the most important information. Prefer short bullets and terse steps over prose; no preamble, padding, restated obvious context, or speculative detail. Add depth only when explicitly asked.
- When creating a task ticket, or rewriting an existing ticket's description, invoke the **create-ticket** skill first and follow its rules and templates. Do not write a ticket from memory.
- All generated code must follow the project's linter and Prettier configuration. **Run the project's lint and format scripts before treating a change as done** — a change that hasn't been linted and formatted is not finished. Where no script exists yet, run the tools directly (`npx eslint`, `npx prettier`) and add the scripts.
- **NEVER silence a linter. No `eslint-disable`, `eslint-disable-next-line`, `eslint-disable-line`, `@ts-ignore`, `@ts-expect-error`, `prettier-ignore`, `istanbul ignore`, or any equivalent suppression, in any language or tool.** A lint error means either the code is wrong or the rule is wrong. Fix the code. If the rule itself is genuinely wrong for this project, STOP and discuss it with the user, then change the rule in the config so it applies everywhere — never suppress it at the call site. Suppressions hide the problem, spread by example, and turn the linter into decoration.
- **NEVER add a code comment without asking the user first and getting an explicit yes.** Default to no comments at all, in any language. The only candidate for a comment is something genuinely off that a reader could not otherwise understand — never a justification for a value, a section header, a TODO, or a restatement of the line below. When you believe a comment is warranted: STOP, describe what you want to write and why, and wait for the green light. Writing it and mentioning it afterwards is a violation. If code seems to need a comment, first make the code clearer instead — better names, an extracted function or constant. Reasoning about why a value was chosen belongs in the ticket, the design file, or the docs, not the source. An existing comment in a file is never licence to add more.
- **Before starting ANY new project, the very first task is defining the linter and Prettier rules** — the configs, the `lint` and `format` scripts, and confirming the two agree with each other. This happens before any feature work, in every package. Invoke the **lint-and-format** skill to do it; it covers the division of responsibility, the rules that must mirror Prettier options, and how to verify the two do not contradict each other. Never begin feature work on a project whose lint and format setup is not settled.

## Agent Team Configuration

### Design-to-page workflow
- When designing Figma frames, the main session (not an agent) records each frame's node-id into the relevant `docs/features/` spec as frames are created.
- The docs-manager writes formal specs only when the user explicitly asks ("write this up as documentation") — never auto-invoked to invent a spec.
- The automated build pipeline (`/design-to-page`: developer → qa → reviewer) runs only after the user approves the spec. Never start it on a guess or an unapproved spec.
- **The design is fixed before the code, never after.** When something in a design is wrong or needs changing, the order is always: (1) make the change in Figma, (2) show the user and wait for explicit confirmation, (3) only then change the code. Never implement a deviation in code first and update the frames afterwards — the Figma file is the source of truth, and code that disagrees with it is a bug even when it looks better. This applies to every design change, however small, including ones the user asks for directly.

When working with agent teams, use these role definitions:

- **Senior Developer**: Implements features based on specs in docs/features/. Follows component folder convention (.tsx, .module.scss, .test.tsx, index.ts). Uses SASS modules, strict TypeScript. Does NOT write tests. Before every tool call that requires permission, provide a short clear description of what the action does and why.
- **Code Reviewer**: Read-only. Reviews for bugs, bad practices, spec compliance. Reports issues with file:line references as Critical/Warning/Minor. Only report issues that are genuinely problematic — verify against actual schema, call sites, and data flow before flagging. Do not pad findings with theoretical edge cases, stylistic nits, or "nice to have" suggestions. If there are no real issues, say so. Before every tool call that requires permission, provide a short clear description of what the action does and why.
- **QA Engineer**: Writes tests using React Testing Library + Jest. Maps acceptance criteria to tests. Colocates test files with components. Before every tool call that requires permission, provide a short clear description of what the action does and why.
- **Docs Manager**: Maintains feature specs and acceptance criteria in docs/features/. Given/When/Then format. Keep specs concise — cover requirements, component changes, acceptance criteria, and key technical decisions only. Avoid exhaustive edge cases, verbose explanations, or repeating what's obvious from the code. Only document what has been explicitly discussed — do not speculatively write up flows (e.g., deletion, error handling) that haven't been decided yet. Specs grow incrementally as features iterate; it's better to add detail later than to write pages that get deleted next iteration. Before every tool call that requires permission, provide a short clear description of what the action does and why.
- **Architect**: Plans architecture, database schemas, folder structure. Breaks features into tasks with dependencies. For a new project, linter and Prettier setup — configs plus the `lint` and `format` scripts — is one of the first tasks in the plan, ahead of feature work. Does NOT implement. Before every tool call that requires permission, provide a short clear description of what the action does and why.

## Social media app (project-specific)

Repo `raristotelov/social-media-app` (renamed from `Picstagram`; the local clone may still be in a `Picstagram/` folder and its git remote may still hold the old URL). The public name is **ShareSnap** — `sharesnap.app`. Board is a Projects v2 board named "Social Media App Board" — project number **2**, owner `@me`. Always target the board by number, never by title, and build issue URLs from the current repo name.

### Creating a task

Go to the repo, create the task, and put it on the board in Todo. All three steps are required — a freshly added board item has NO Status until one is set explicitly:

1. Create the issue in the repo (GitHub MCP `issue_write`, or `gh issue create`). Leave it **unassigned**.
2. Add it to the board: `gh project item-add 2 --owner @me --url <issue-url>`
3. Set Status: `gh project item-edit 2 --owner @me --url <issue-url> --field "Status" --value "Todo"`

- New tasks are always created **unassigned** and **in Todo**. Assign to `raristotelov` only when work actually starts on the task, never at creation time.
- Status options are exactly: `Todo`, `In Progress`, `Done`.
- Board operations require the `gh` CLI — Projects v2 is GraphQL-only and the GitHub MCP server exposes no project/board tools. Use the MCP server for issues/PRs/repo contents, `gh` for anything board-related.
- `item-add` and `item-edit` print nothing on success. Always verify by reading state back: `gh project item-list 2 --owner @me --format json`.
- Designs — use as the `<figma-link>` in page redesign tickets: https://www.figma.com/design/bDyuGKpRh2vP1DlElilDaw/Social-Media-App-Design
- Colour tokens live in `docs/style-guide.md`. The two whites are `background/surface` (`#FFFFFF` light → `#161616` dark) and `static/white` (`#FFFFFF` in both).
- **Breakpoints.** Design canvases are Mobile 390, Tablet 768, Desktop 1440 — these are the widths to check against, NOT the CSS breakpoints. The CSS ranges are: **mobile below 600, tablet 600–1279, desktop 1280 and up.** 600 is Android/Material's Compact→Medium boundary (Google reports it covers 99.96% of phones in portrait); it clears the widest phone in portrait (~430) and puts 7-inch tablets (~600) and every iPad portrait (incl. the 744 mini) on tablet rules. Don't go lower — the tablet layouts run out of room around 540–560. Landscape tablet reuses the desktop rules. Every page ticket covers all three canvases, in light and dark.
- **300px is the hard floor.** Every page stays usable all the way down to a 300px viewport — no horizontal scroll, no clipped, overlapping or overflowing content, every control still reachable and tappable. The 390 canvas defines the *design*; 300 defines the *limit*, so check it alongside the three canvases before calling page work done. Below 640 prefer fluid values (percentages, `minmax(0, 1fr)`, `calc()`) over fixed px widths so the layout keeps shrinking instead of breaking at a threshold.
- A component's internal spacing should key off **its own width, not the viewport**, where the two can disagree — a 600px card must not inherit phone spacing just because the window is narrow. Prefer a container query over a viewport media query for that case.
- ESLint and Prettier configs exist in both `client/` and `server/`, but **neither `package.json` has a `lint` or `format` script yet**. Add them when work starts on the first ticket, then run them before finishing any change.

### Working on a task

1. **Before starting any work, ask which ticket it belongs to.** Never start on an untracked change. If there is no ticket for it, ask how to proceed rather than deciding.
2. Once the ticket is known, assign it and move it to In Progress before writing any code:
   - `gh issue edit <n> -R raristotelov/social-media-app --add-assignee raristotelov`
   - `gh project item-edit 2 --owner @me --url <issue-url> --field "Status" --value "In Progress"`
3. When the work is finished, move it to Done and close the issue:
   - `gh project item-edit 2 --owner @me --url <issue-url> --field "Status" --value "Done"`
   - `gh issue close <n> -R raristotelov/social-media-app`
4. Verify every move by reading the state back — these commands print nothing on success.
